# Design note

## 1. Approach and alternatives

**Entity detection and resolution.** The pipeline builds a gazetteer per entity type from the reference CSVs (name + `|`-separated aliases, case-insensitive), scans each email for exact/alias matches, and falls back to regex heuristics (road-number patterns, "...Council"/"...Local Resilience Forum"/"Storm <Name>"/"...Rest Centre" etc.) for entities absent from any reference list. Fallback matches are fuzzy-matched (`rapidfuzz`, threshold 90) against the gazetteer and against entities already minted earlier in the run, before finally minting a new entity ID. This was chosen over a local NER model (spaCy or a small local LLM): the reference lists already give a strong, dataset-agnostic signal a generic NER model would have to relearn; a model-download-and-inference step adds fragility against "no network at run time" and "10 minutes, CPU-only" on unattended, unreviewed data; and rule-based resolution is fully auditable — every decision traces to an exact rule. The cost is recall: paraphrased mentions hitting no gazetteer key or fallback pattern are simply missed, and the fallback patterns are hand-written for UK civil-contingencies vocabulary, so a very differently-worded private dataset would degrade that path (not the gazetteer path, which is fully data-driven).

**Relation extraction.** Any two resolved entities whose mentions fall within a fixed character window (400 chars) are a candidate pair; a cue-keyword table (`rules/relations.yaml`, keyed by relation type) decides whether — and which — relation fires, constrained by a fixed `(from_type, to_type)` pair per relation type. This is deliberately the most editable part: adding a relation type is a YAML edit plus one line declaring its entity-type pair, no code change. The alternative considered, dependency-parse-based extraction (e.g. spaCy, walking the syntactic path between two mentions to classify the relation from verb/preposition structure), would likely give better precision on well-formed prose, but is a poor fit here: much of the corpus is semi-structured sitrep text ("3. AGENCIES RESPONDING\nNCIC, Drinking Water Inspectorate, ...") that parses poorly as prose, and it reintroduces the same model-dependency risk. The weakness of co-occurrence showed up directly during implementation: an initial keyword guess produced zero `COORDINATED_BY`/`RESPONDS_TO`/`OPERATES` relations against 160 `AFFECTS`, and the real emails turned out to use "Lead:", "RESPONDING", "run by" rather than the words first guessed. Fixing it was a YAML edit — exactly the point of an extensible rule table — but also evidence that keyword coverage is dataset-specific and will need the same correction on the private dataset.

**Observation extraction.** Each resolved entity is checked for entity-type-specific status keywords (`rules/observations.yaml`) within a 120-character window around its mention; a hit produces a `(property, value)` observation timestamped by the email's `Date` header and attributed to the source email. No observation overwrites another — every report is kept, so the store answers both "what do we currently believe" (latest observation) and "how did this change" (full history), matching the brief's requirement to track a road closing then reopening, or an early report later corrected.

**With a frontier LLM endpoint**, most of this hand-written pattern-matching becomes unnecessary. Entity detection, resolution, relation typing and observation extraction are all naturally one structured-output extraction prompt per email: give the model the reference lists as candidate entities plus a JSON schema, and let it do joint extraction and resolution in one pass — likely beating this rule-based system on recall for unusually-worded reports, with no dataset-specific keyword tuning. The trade is exactly what the brief requires: zero hosted-model calls at run time and auditable behaviour on unreviewed data. A realistic middle ground worth exploring with more time is a local small LLM used only as a second pass over paragraphs where the rule-based pass found nothing, rather than replacing the deterministic core.

## 2. Evaluation

No labels are provided, and the brief asks how to get them or work without them.

**Getting labels.** The cheapest source is a small, double-annotated sample — 20-30 emails chosen to cover the corpus's variety (plain text, multipart, HTML-only, dense sitrep-style, casual reply-style), independently annotated against the entity and relation types, disagreements adjudicated into a gold set. That gives precision/recall for detection, resolution (assigning the *right* entity, not just a plausible one — a confident wrong resolution is worse than a miss), relation extraction and observation extraction, scored separately, since the brief's own "linking does not replace entity resolution" implies they should be evaluated separately too.

**Working without labels, and monitoring new data.** Several proxies need no annotation: reference-list coverage (what fraction of each gazetteer is ever matched — near-zero for a type clearly discussed in the emails flags a resolution problem); new-entity rate (a spike on the private dataset relative to the provided one cheaply signals that fallback regexes or keyword tables need attention there, exactly as happened here); and relation/observation trigger-rate skew (one relation type firing far more than others, as `OPERATES` did once its keyword was widened, deserves a manual spot-check even without ground truth). For end-to-end quality, a handful of specific incidents can be manually traced through the raw emails against the observation timeline produced — doesn't scale, but directly tests the brief's core use case and would have caught the relation-keyword gap without aggregate counts. Continuous monitoring on the private dataset would run these proxies on every run, flagging anything outside the range seen on the provided dataset, rather than assuming silence means correctness.

## 3. Trade-offs and next steps

The main limitations follow directly from the rule-based design. Recall drops on paraphrased or unusually-worded text that hits no gazetteer key, fallback regex, or cue keyword — there is no generalization beyond what's explicitly encoded, which is why keyword-tuning mattered during implementation and why the private dataset should be expected to need the same tuning. The regex fallback for new entities is the most brittle piece: tuned to UK civil-contingencies phrasing ("Rest Centre", "Treatment Works", "Council"), it will simply miss entities phrased differently, with no fallback of its own. Co-occurrence windowing has no coreference resolution — "it", "the road", "the council" referring back to an earlier mention are invisible — and the fixed character window is a blunt instrument that can miss genuinely related entities separated by intervening text and, as observed directly on the real run, over-trigger relations (`OPERATES` fired 1511 times across 271 emails once its keyword list was widened) when several mentions cluster within one window without actually being related.

With more time, the highest-value next steps: basic coreference resolution (a rule-based "resolve pronoun/definite-NP to the most recently mentioned same-type entity" pass would meaningfully improve relation and observation recall on reply chains); a more structurally-aware relation window (per-sentence or per-bullet-point, not a fixed character count) to cut the `OPERATES` over-triggering seen on the real data; a small trained classifier (logistic regression over lightweight features — distance, keyword presence, entity-type pair) for relation typing once a labelled sample exists, replacing the keyword table's binary decision with a calibrated score; and an active-learning loop routing the pipeline's lowest-confidence resolutions and relations to a human reviewer, feeding corrections back into the gazetteer aliases and rule tables already in place.
